## 第一層：記憶體優化（RAM）

### 現況分析

- 43GB 記憶體完全閒置
- 可承載 20GB+ 熱資料 + 10GB 模型緩存

### 策略一：本地向量知識庫（RAG）

**目標：** 建立 20GB+ 文件向量庫，常駐記憶體

```
規劃配置：
├── 向量資料庫（ChromaDB/FAISS）：15GB
│   ├── TLS 商業文件 embedding
│   ├── 技術文檔向量
│   └── 對話歷史語意索引
├── 模型緩存層：20GB
│   ├── embedding model（all-MiniLM-L6-v2）：500MB
│   ├── Sentence Transformers × 2：1.5GB
│   └── quantization LLMs：8GB
└── 熱門資料讀取區：8GB
    └── 常用文件熱副本
```

**技術實現步驟：**

1. 安裝 `chromadb` / `faiss-cpu`（或 `faiss-metal` GPU加速）
2. 建立文件 intake pipeline：`docs/` → `text_splitter` → `embedding` → `vectorDB`
3. 設定開機自動載入向量庫腳本（`launchd` 或 `systemd`）
4. 配置 HNSW 索引參數：`M=64, efConstruction=200`

**預期效果：**

- 文件檢索延遲：從磁碟讀取的 ~2000ms → 記憶體內 ~5ms（**400倍加速**）
- 閒置 RAM：57% → 95%+ 使用

### 策略二：模型熱門組合待命

**常駐記憶體模型（建議）：**

| 模型                 | 用途           | 記憶體佔用 | 應該常駐？  |
| -------------------- | -------------- | ---------- | ----------- |
| all-MiniLM-L6-v2     | 文件 embedding | 500MB      | ✅ 強烈建議 |

**組合策略：**

## 第二層：並發處理優化（CPU）

### 現況分析

- CPU 94% 閒置 = 28核幾乎完全未用
- 可承載 10-15 個並發子代理任務

### 策略一：子代理並發架構

**目標：** CPU 利用率從 6% → 40%+

```
架構設計：
┌─────────────────────────────────────────────┐
│              主代理（協調者）                 │
│  任務隊列 → 優先級排序 → 分發給子代理池       │
└─────────────────────────────────────────────┘
          │           │           │
    ┌─────┴───┐ ┌─────┴───┐ ┌─────┴───┐
    │ 子代理1  │ │ 子代理2  │ │ 子代理N  │
    │ (核心A)  │ │ (核心B)  │ │ (核心N)  │
    └─────────┘ └─────────┘ └─────────┘
          ↓           ↓           ↓
    ┌─────────────────────────────────┐
    │     共享向量知識庫（記憶體）        │
    └─────────────────────────────────┘
```

**OpenClaw 子代理配置建議：**

```yaml
# openclaw.yaml 或等效配置
subagents:
  max_concurrent: 12 # 同時最多12個子代理
  default_cores: 2 # 每個子代理分配2核
  affinity: "p-core-first" # 優先使用效能核心

scheduler:
  min_tasks_per_agent: 3 # 任務少於3個不啟新子代理
  queue_timeout: 300 # 排隊超時300秒
```

**預期 CPU 利用率提升：**

- 單任務：6%
- 12 並發子代理 × 2核：24 核使用 → 24/28 = **85%+ 理論**
- 實際穩態目標：**40-60%**

### 策略二：任務排程器（凌晨時段）

**離峰時段自動化任務：**

| 時段        | 任務類型     | 說明                 |

| 01:00-04:00 | 模型預訓練   | 微調、embedding 更新 |

## 第三層：硬碟空間利用（Disk）

### 現況分析

- 970GB 完全閒置
- 可規劃：備份系統 + 快取層 + 資料湖

### 策略一：本地備份系統

**備份架構（3-2-1 原則）：**

```
├── 本地備份（Time Machine 增量）
│   └── 每小時增量快照，保留30天
├── 資料庫備份（PostgreSQL/Wal-g）
│   ├── 每6小時全量 + continuous WAL
│   └── 壓縮率目標：70%（1TB → 300GB）
└── 知識庫版本化
    ├── 每週向量庫快照
    └── Git-like diff 增量備份
```

**預期磁碟使用：**

- 備份系統：200GB（預留成長）
- 資料湖：300GB
- **總計：500GB（仍保留 470GB 閒置）**

### 策略二：快取加速層

**多級快取架構：**

```
L1：記憶體快取（RAMDisk）
    └── 常用 embedding 結果、活躍對話 context
    └── 大小：10GB RAMDisk
    └── 速度：~50GB/s

L2：本地 SSD 快取（ Velasco/Boost ）
    └── 任務輸出、查詢結果、模型權重
    └── 大小：200GB
    └── 速度：~3GB/s

L3：冷資料歸檔（HDD/雲端）
    └── 歷史文件、歸檔數據
    └── 速度：~100MB/s
```

**快取命中加速效果：**

- 首次查詢：~2000ms
- L1 快取命中：~5ms（**400倍加速**）
- L2 快取命中：~50ms（**40倍加速**）
- **綜合重複任務加速：平均 10 倍以上**
